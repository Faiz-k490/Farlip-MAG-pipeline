# FaRLiP Comparative Genomics Pipeline

A config-driven pipeline that locks in the canonical 21-gene Far-Red Light
Photoacclimation (FaRLiP) cluster organism (*Leptolyngbya* sp. JSC-1) plus a polar
cyanobacterial MAG corpus, predicts ORFs in every assembly, builds HMM profiles
for the 21 FaRLiP genes, runs synteny-aware HMM searches across the MAGs, and
exports a browsable Obsidian markdown vault of candidates.

**Phase 1** (ingestion), **Phase 2** (16S extraction + SILVA/GTDB-Tk
taxonomic-placement routing + extremophile vault), **Phase 3** (FaRLiP
detection), and **Phase 4** (genome quality assessment) are all shipped. See
[`DEVLOG.md`](DEVLOG.md) for the change history and
[`DATA_SOURCES.md`](DATA_SOURCES.md) for the canonical lock-in spec.

> **Runtime note.** The in-process Python stages (Phases 1, 3, and 4) run
> end-to-end in ~135 s on a 12-core M-series laptop for the 39-assembly
> reference corpus. **CheckM2, GTDB-Tk, and SILVA SINA are not run by
> this pipeline.** Phase 2 and Phase 4 emit shell scripts
> (`scripts/run_gtdbtk.sh`, `scripts/run_checkm2.sh`, and
> `data/ssu/silva_sina_input.fasta`) that you execute on whatever
> infrastructure has those tools and reference databases installed
> (GTDB R226 alone is ~141 GB); their wall time is not included in the
> 135 s figure.

| | |
|---|---|
| **Primary anchor** | *Leptolyngbya* sp. JSC-1 (`GCF_000733415.1`) |
| **MAG test corpus** | ENA `PRJEB59431` (37 polar cyanobacterial MAGs) |

## How the Pipeline Works

**A MAG file** (this is just DNA sequence, like `ATCGATCG...`)

### Phase 1: Download and organize
- Pipeline downloads your MAG files from NCBI/ENA
- Organizes them in folders
- Records what it downloaded in a manifest

### Phase 2: Find the "barcode gene" (16S)
- Pipeline scans each MAG looking for the 16S ribosomal RNA gene
- If found → route to SILVA database for identification
- If not found → route to GTDB database for identification
- Creates shell scripts for you to run later (pipeline doesn't run these itself)

### Phase 3: Find proteins and look for FaRLiP
- **This is where proteins come from!**
- Pipeline runs Prodigal on your DNA sequence
- Prodigal is a tool that reads DNA and predicts "this part codes for a protein"
- It converts: `ATCGATCG...` → protein sequences like `MKRLLV...`
- Pipeline then runs HMMER to search those proteins for FaRLiP markers
- Records which MAGs have FaRLiP genes

### Phase 4: Check genome quality
- Pipeline runs BUSCO to check if your MAG is good quality
- BUSCO looks for essential genes that all bacteria should have
- If MAG has most essential genes → good quality
- If MAG is missing many → poor quality

## Running on Your Own MAGs

```bash
# 1. Set up environment
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Tell NCBI who you are (their usage policy)
export NCBI_EMAIL="you@your-institution.edu"
# Optional: 10 req/s instead of 3 req/s
export NCBI_API_KEY="..."

# 3. Add your own MAGs to the manifest (optional)
# Edit config/manifest.yaml to include your MAG files, then:
python -m src.pipeline ingest

# 4. Phase 1: download references + databases (~450 MB)
python -m src.pipeline fetch all
python -m src.pipeline status
python -m src.pipeline verify

# 5. Phase 2: 16S extraction + generate shell scripts for taxonomic ID
#    (requires barrnap on PATH)
python -m src.pipeline_phase2 all
python -m src.pipeline_phase2 status

# 6. Run the external taxonomic identification scripts (manual step)
#    These are generated by Phase 2 - you run them yourself:
bash scripts/run_gtdbtk.sh    # For MAGs without 16S
# SILVA SINA input is in data/ssu/silva_sina_input.fasta

# 7. Phase 3: find proteins and detect FaRLiP
python -m src.pipeline_phase3 all
python -m src.pipeline_phase3 status

# 8. Phase 4: check genome quality and generate final report
python -m src.pipeline_phase4 all
python -m src.pipeline_phase4 status

# 9. View results
# Final filtered MAG list: data/qc_filtered_mags.tsv
# Detailed results: data/phase4_manifest.tsv
```

## Quickstart (Original Reference Corpus)

Or use the wrapper for the original 39 MAG corpus:

```bash
./scripts/fetch_all.sh                    # same as `fetch all`
./scripts/fetch_all.sh --limit 3          # smoke test: 3 MAGs per BioProject
```

Output lands under `data/` (gitignored). Every artifact is recorded in `data/manifest.tsv`.

## CLI Reference

### Phase 1 - ingestion (`src.pipeline`)

```
python -m src.pipeline fetch {references|mags|databases|all} [--overwrite] [--limit N]
python -m src.pipeline verify
python -m src.pipeline status
```

* `--overwrite` re-downloads even if the file already exists with a matching hash.
* `--limit N` caps the number of assemblies fetched per BioProject. Use it for smoke
  testing before committing to the full ~450 MB download.
* The pipeline is **idempotent**: artifacts already present (with non-zero size) are
  hashed in place and the manifest row is updated without redownloading.

### Phase 2 - SSU extraction + taxonomic-placement routing (`src.pipeline_phase2`)

```
python -m src.pipeline_phase2 extract-16S       [--overwrite] [--accession ACC]...
                                                  [--threads N] [--kingdom {bac|arc|euk|mito}]
                                                  [--evalue E] [--reject R]
python -m src.pipeline_phase2 bundle-silva
python -m src.pipeline_phase2 gen-gtdbtk-script [--threads N]
python -m src.pipeline_phase2 all               [--overwrite]
python -m src.pipeline_phase2 status
```

* **Requires `barrnap` on PATH.** Install via `conda install -c bioconda
  barrnap` (or any equivalent). The pipeline never auto-installs `barrnap`;
  `extract-16S` exits 2 with a clear message when it cannot find the binary.
* **`extract-16S`** runs `barrnap` once per assembly listed in
  `data/manifest.tsv`, writes `data/ssu/<acc>.barrnap.gff` + `<acc>.16S.fasta`
  + an idempotency stamp, and upserts a row into `data/ssu/routing_log.tsv`.
  Each MAG receives a `decision` tag of `silva` (>=1 16S record) or `gtdbtk`
  (no 16S). Per-MAG stamps key on the input FASTA SHA-256 and the exact
  `barrnap` argv so a parameter change forces a re-run.
* **`bundle-silva`** concatenates every `decision == silva` MAG's
  `<acc>.16S.fasta` into a single `data/ssu/silva_sina_input.fasta` ready
  for SILVA SINA submission (web upload at <https://www.arb-silva.de/aligner/>
  or the SINA CLI against the on-disk SILVA 138.2 NR99 FASTA).
* **`gen-gtdbtk-script`** renders `scripts/run_gtdbtk.sh` (+
  `data/ssu/gtdbtk_batchfile.tsv`) for every `decision == gtdbtk` MAG.
  Gzipped ENA assemblies are decompressed once into
  `data/ssu/gtdbtk_input/<acc>.fna` so `--extension fna` works for the
  whole batch. The script begins with `set -euo pipefail`, requires
  `GTDBTK_DATA_PATH` to be exported, and is `bash -n`-clean.
* **`status`** prints whether the routing log, SILVA bundle, and GTDB-Tk
  script are present plus a count of MAGs routed each way.

Phase 2 progress is recorded in `data/phase2_manifest.tsv` (per-stage
status + wall time) for resumability mirroring Phase 3 / Phase 4.

### Phase 3 - FaRLiP detection (`src.pipeline_phase3`)

```
python -m src.pipeline_phase3 orf-predict   [--overwrite] [--accession ACC]...
python -m src.pipeline_phase3 build-profiles [--overwrite]
python -m src.pipeline_phase3 search         [--overwrite] [--accession ACC]...
python -m src.pipeline_phase3 parse-synteny  [--overwrite]
python -m src.pipeline_phase3 export-vault   [--overwrite]
python -m src.pipeline_phase3 all            [--overwrite]
python -m src.pipeline_phase3 status
```

* Subcommands are independently re-runnable. Stamp files under `data/orfs/` and
  the SHA-256 of every input FASTA make ORF prediction strictly idempotent;
  hmmsearch and the synteny / vault stages overwrite their outputs on each run.
* `data/phase3_manifest.tsv` records every stage's status, output path, and
  wall-time so `all` can resume from a partial run and so downstream auditors can
  reconstruct exactly what produced which file.

### Phase 4 - genome quality assessment (`src.pipeline_phase4`)

```
python -m src.pipeline_phase4 fetch-markers              [--overwrite]
python -m src.pipeline_phase4 assess                     [--overwrite] [--accession ACC]...
python -m src.pipeline_phase4 gen-checkm2-script
python -m src.pipeline_phase4 ingest-checkm2             [--accession ACC]...
python -m src.pipeline_phase4 report                     [--require-farlip] [--include-low]
python -m src.pipeline_phase4 update-vault               [--overwrite]
python -m src.pipeline_phase4 export-extremophile-vault  [--routing-log PATH]
python -m src.pipeline_phase4 all                        [--overwrite]
python -m src.pipeline_phase4 status
```

* **Default (in-process) QC path.** `assess` runs `pyhmmer` against a bacterial
  single-copy ortholog (SCO) HMM database (BUSCO `bacteria_odb10`, 124 markers,
  ~6 MB) fetched once by `fetch-markers`. Each MAG receives a per-marker bit
  score gated by BUSCO's own `scores_cutoff` file (the canonical paralog
  filter) plus an E-value floor. Outputs land in `data/qc_assessor/<acc>.qc.tsv`.
* **Opt-in CheckM2 cross-check.** `gen-checkm2-script` emits
  `scripts/run_checkm2.sh`. You run the script yourself on any machine that has
  CheckM2 + the CheckM2 diamond DB installed (`export CHECKM2DB=...`); the
  resulting `data/checkm2_results/<acc>/quality_report.tsv` files are then
  picked up by `ingest-checkm2`. When both sources exist for the same MAG,
  `report` prefers CheckM2.
* **`report`** joins everything (pyhmmer / CheckM2 QC + Phase 3 FaRLiP
  per-MAG roll-up + Phase 1 manifest) into `data/qc_report.tsv` (every MAG)
  and `data/qc_filtered_mags.tsv` (only `recommended_for_phylogeny == True`,
  i.e. MIMAG HIGH/MEDIUM **and** a FaRLiP candidate). Pass `--require-farlip`
  to drop MAGs with no FaRLiP markers, `--include-low` to keep MIMAG LOW.
* **`update-vault`** re-renders the Phase 3 Obsidian vault, adding
  `completeness`, `contamination`, `n50_contig`, `genome_size_bp`,
  `qc_quality`, `qc_source`, and `recommended_for_phylogeny` to every
  per-MAG YAML frontmatter, plus a "## Quality" section grouped by tier
  in `Phase_3_Master_Index.md`.
* **`export-extremophile-vault`** renders `data/extremophile_vault/`:
  one per-MAG markdown file per `recommended_for_phylogeny == True` row in
  `qc_filtered_mags.tsv` plus the master index
  `High_Quality_Extremophile_Genomes.md`. Each per-MAG note carries the
  exact five-key frontmatter mandated by the assignment - `Accession`,
  `Completeness`, `Contamination`, `Taxonomic_Placement`,
  `FaRLiP_Cluster_Present` - with `FaRLiP_Cluster_Present` left **blank**
  for manual review. `Taxonomic_Placement` is filled with
  `"SILVA SINA: pending"` / `"GTDB-Tk: pending"` placeholders when the
  Phase 2 routing log exists at `data/ssu/routing_log.tsv`; otherwise the
  slot is left empty. The exporter is also part of `all`, so the standard
  Phase 4 workflow produces both vaults.
* `data/phase4_manifest.tsv` records every stage's status, output path, and
  wall time, mirroring Phase 3 for resumability.

## Configuration

Three config files drive every fetcher. Editing them changes what is fetched without
touching any Python.

| File | Purpose |
|---|---|
| [`config/references.json`](config/references.json) | FaRLiP reference anchors. `primary` is the canonical 21-gene cluster organism; `secondary` is a list (possibly empty) for cross-checks. |
| [`config/extremophiles.json`](config/extremophiles.json) | MAG sources. `bioprojects` = whole-project enumeration; `individual_accessions` = one-offs. |
| [`config/databases.yaml`](config/databases.yaml) | SILVA + GTDB versions and download URLs. |
| [`config/farlip_genes.yaml`](config/farlip_genes.yaml) | The 21-gene FaRLiP catalog used by `src/profile_builder.py`. Each entry pins a JSC-1 locus_tag + RefSeq protein_id with fuzzy fallbacks (gene_tag, product_substring) for future anchors. |
| [`config/qc_markers.yaml`](config/qc_markers.yaml) | Single-copy ortholog marker HMM sources for Phase 4 QC. Default = BUSCO `bacteria_odb10` (124 markers, ~6 MB, stable URL + SHA-256). `gtdb_bac120_local` provides an opt-in escape hatch for users who already have GTDB-Tk's bac120 markers extracted locally. |

### Adding a single accession

Open `config/extremophiles.json`, append to `individual_accessions`:

```json
{
  "accession": "GCA_XXXXXXXXX.X",
  "source": "NCBI",
  "label": "sample_descriptor",
  "biome": "cave",
  "notes": "Short provenance note"
}
```

Then re-run `python -m src.pipeline fetch mags`. The pipeline auto-dispatches NCBI
accessions to the Datasets v2 API and ENA accessions to the ENA Browser API; existing
artifacts are skipped.

## Tests

```bash
.venv/bin/python -m pytest tests/ -v
```

140 tests, all offline-only (20 Phase 1 + 36 Phase 2 / extremophile vault +
37 Phase 3 + 47 Phase 4). Phase 1 mocks NCBI Datasets and the ENA Portal;
Phase 3 uses tiny in-memory FASTA / GFF fixtures plus hand-rolled HMMER
domtblout fixtures; Phase 4 mocks the BUSCO tarball, the per-MAG `pyhmmer`
scan, and CheckM2 `quality_report.tsv` parsing. Phase 2 mocks `subprocess.run`
so `barrnap` is never actually invoked - a stub GFF3 fixture drives the
extraction / routing / bundling code paths, and the generated GTDB-Tk shell
script is syntax-checked with `bash -n`. The suite works with no network and
no third-party binaries on PATH.

| Iteration | Status | Scope |
|---|---|---|
| **1** | shipped | Ingestion + manifest. Reference, MAGs, SILVA, GTDB on disk, SHA-256-verified. |
| **2** | shipped | `barrnap` 16S extraction per MAG + per-decision routing log (`silva` / `gtdbtk`) + SILVA SINA multi-FASTA bundle + generated `scripts/run_gtdbtk.sh` for genome-wide marker classification on MAGs without recoverable 16S. SILVA SINA and GTDB-Tk themselves remain user-run (network upload / 141 GB reference data). |
| **2.1** | planned | `ingest-silva` / `ingest-gtdbtk` that parse the SINA result file and the GTDB-Tk `bac120.summary.tsv` and overwrite `Taxonomic_Placement` in every per-MAG extremophile-vault note from `pending` to the resolved species / lineage. Symmetric to Phase 4's `ingest-checkm2`. |
| **3** | shipped | ORF prediction (pyrodigal meta) + 21 single-sequence HMMs from JSC-1 + pyhmmer hmmsearch + 3-in-10kb candidate trigger / 30kb classification window with EDGE_TRUNCATED tagging + Obsidian export. **Validation:** JSC-1 -> FULL_CLUSTER (21/21 markers in 30 kb on contig NZ_KL662192.1). |
| **3.1** | planned | Integrate Chlorogloeopsis fritschii PCC 9212 as secondary anchor. Switch `profile_builder` from single-sequence to MSA-based via mafft subprocess. |
| **4** | shipped | Per-MAG completeness / contamination / N50 / genome-size via in-process pyhmmer against BUSCO `bacteria_odb10` (124 SCOs, with per-HMM `scores_cutoff` paralog gate) + MIMAG HIGH/MEDIUM/LOW tier assignment + optional CheckM2 shell-script cross-check + QC-aware Obsidian re-render. **Validation:** JSC-1 -> 94.4% completeness / 8.1% contamination (MIMAG MEDIUM, within published BUSCO-vs-CheckM2 envelope for cyanobacterial RefSeq assemblies); 39-MAG corpus -> 1 HIGH / 36 MEDIUM / 2 LOW; 36 recommended for phylogeny. |
| **4.5** | planned | Per-domain marker sets (archaeal `ar122` etc.) for non-bacterial MAGs once they land in the corpus. |
| **5** | planned | Phylogenetic placement of `qc_filtered_mags.tsv` via SILVA 16S (Phase 1 already has SILVA 138.2 NR99) and/or GTDB-Tk placement (Phase 1 already has GTDB R226 metadata). Tree builder + biome cross-validation. |

The Phase 1 + Phase 3 + Phase 4 design choices specifically support the later stages:

* NCBI Datasets bundles include protein FASTA -> already consumed in Phase 3.
* ENA assemblies arrive as gzipped FASTA -> `orf_predictor` reads gzip natively.
* `data/manifest.tsv` is the unified Phase 1 input; `data/phase3_manifest.tsv`
  and `data/phase4_manifest.tsv` record every later stage's status and are the
  resumability anchors for their respective `all` subcommands.
* Phase 4 reuses the Phase 3 `.faa` outputs (no re-prediction) and writes both
  CheckM2 and pyhmmer rows into the *same* schema, so the reporter does not
  need to know which engine ran.
